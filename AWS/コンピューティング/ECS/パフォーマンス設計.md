# パフォーマンス設計
## Application Auto Scaling
※CloudWatchで定めたメトリクスの閾値に従ってスケールアウト・スケールインが実行される

### ステップスケーリングポリシー
- スケールアウト・スケールインさせる条件に「ステップ」を設けることで段階的にスケールアクションを設定できるポリシー
  - スケーリングイベントが発生している途中で別のイベントが発生しても応答する
  - スケールアウト後も負荷が高まっている場合においても、ステップを複数(CPU使用率60%以上は10%のリソースを増加、80%以上は30%のリソースを増加)定義しておくことで段階的にスケールアウトが可能
  - CPU使用率40%以下は10%のリソースを減少させるといった、削除のポリシーも追加することで、負荷に応じたタスク増減を制御可能
 
### ターゲット追跡スケーリングポリシー
- 指定したメトリクスのターゲット値を維持するようにスケールアウト・スケールインが制御されるポリシー
  - メトリクスがターゲット値を超えている場合のみスケールアウトする
  -  スケールアウトは高速に動作し、スケールインは緩やかに実行される
  -  複数メトリクスのターゲット値を設定可能 ⇒ いずれかのターゲット値を超過すればスケールアウトが実行されるが、スケールインはすべてのターゲット値が下回っている場合に実行される

### 予測スケーリングポリシー
- 過去のメトリクス履歴から今後のリソース需要の傾向を予測し、事前にスケーリングを実行するポリシー
  - 毎週末の定期的なアクセス増や日々の定期時刻によるバッチ処理など、周期性のあるワークロードにおけるパフォーマンス設計として有効
  - 日々の傾向に基づいて動作するのはスケールアウトのみであり、スケールインは行われないため、他のスケーリングポリシーとの併用が前提となるポリシー

### スケジュールされたアクション
- 特定の時間を指定してECSタスクを増減させることが可能なため、あらかじめ需要が予測できるユースケースに有効

## パフォーマンステスト観点
### 実際にテストを実施する場合、以下観点を確認するとよさそう
- どのようなバリエーションでテストするか(通常不可、想定外の不可、急激な負荷変動、長時間稼働など)
- 期待する一連のCloudWatchメトリクスが取得できているか
- アプリケーションログからエラーが出力されていないか
- ログ出力の内容は適切か
- AutoScalingのスケールアウト・スケールインは設定されているか
### CloudWatchメトリクスでの確認事項
- パフォーマンス要件で定義したリクエスト量が満たせているか
- タスク定義に割り当てたCPU/メモリリソースに対して、余剰や逼迫が発生していないか
- タスク定義内の各コンテナに割り当てたCPU/メモリリソースに対して、余剰や逼迫が発生していないか
- アプリケーションリソース以外でボトルネックになっている箇所がないか(ディスク、ネットワークなど)
- AutoScalingのスケールアウト/スケールインは正しく発動するか
- スケールアウト/スケールイン時にアプリケーションエラーが発生していないか(期待するHTTPステータスコードが応答されるか)
